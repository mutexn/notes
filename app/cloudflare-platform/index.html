Cloudflare プラットフォーム

通常のサーバーと DB から読み解く

Web アプリケーションの定番の構成は、ロードバランサの後ろにアプリケーションサーバーを並べ、その奥にリレーショナルデータベースとオブジェクトストレージを置く形です。Cloudflare の開発者プラットフォームも、同じ仕事をする部品をひととおり揃えています。

ただし、部品の形が違います。サーバーは常駐せず、リクエストのたびに世界中のデータセンターで起動します。データベースは、1 台の大きなサーバーではなく、小さな単位にいくつも分けて持つことが前提になっています。

このノートでは、Workers・Durable Objects・D1・R2・AI Gateway を中心に、各部品が通常の構成のどれに当たり、どこが違うのかを図で確かめていきます。序章で全体の地図を描き、各章で 1 つずつ掘り下げ、終章で組み立てます。

章

  • 序章

    全体の地図 — 通常の構成と並べてみる

    ロードバランサ・アプリケーションサーバー・RDB・オブジェクトストレージという定番の構成に、Cloudflare の部品を重ねる。
    エッジで動くとはどういうことか、状態をどこに置くのかを先に押さえる。

  • 第1章

    Workers — 常駐しないサーバー準備中

    プロセスやコンテナではなく、V8 の isolate の上でリクエストごとに動く。
    何が速くなり、何ができなくなるのか。接続文字列の代わりに使う binding の考え方も扱う。

  • 第2章

    Durable Objects — 名前で 1 つに決まるサーバー準備中

    通常の構成では Redis やロックで実現する「1 か所で順に処理する」仕組みを、部品そのものが持っている。
    チャットルームやカウンターを例に、単一スレッドと内蔵ストレージの意味を確かめる。

  • 第3章

    D1 — 小さく分けて持つ RDB準備中

    PostgreSQL や MySQL のサーバーと、SQLite を土台にした D1 を比べる。
    接続の扱い、容量の上限、読み取りレプリカ、テナントごとに DB を分ける設計を見ていく。

  • 第4章

    R2 — エグレス料金のないオブジェクトストレージ準備中

    S3 と同じ API で使えるオブジェクトストレージ。
    S3 ＋ CDN の構成と比べながら、料金の構造と Workers からの使い方を確かめる。

  • 第5章

    AI Gateway — LLM の前に置く関所準備中

    アプリから LLM の API を直接呼ぶ構成と、間に Gateway を挟む構成を比べる。
    キャッシュ・レート制限・ログ・フォールバックを 1 か所に集める意味と、Workers AI との違いを扱う。

  • 終章

    組み立てる — 同じアプリを 2 通りに描く準備中

    1 つのアプリを、通常の構成と Cloudflare の構成で並べて描く。
    常時稼働の課金と CPU 時間の課金の違い、向いている仕事と向いていない仕事をまとめる。
