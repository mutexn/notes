全体の地図

通常の構成と並べてみる

部品の名前は違っても、仕事の分担はほとんど同じ。違うのは、それぞれが「どこで」「どの単位で」動くかだ。

Cloudflare の開発者プラットフォームには、名前だけでは役割の分からない部品が並んでいます。Workers、Durable Objects、D1、R2、KV、AI Gateway。最初に個別の説明を読むと、どれも便利そうに見えて、かえって全体像がつかめません。

そこでこの序章では、よく知っている Web アプリケーションの構成を先に描き、その上に Cloudflare の部品を 1 つずつ重ねていきます。各章で掘り下げる前に、地図を手に入れておくのが目的です。

このページの前提は次のとおりです。

  • Web サーバー、RDB、オブジェクトストレージを使った開発の経験があることを想定する
  • コードはほとんど載せず、図と文章で構成を示す
  • 各サービスの提供状況と制限は、2026 年 10 月時点の公式ドキュメントに基づく

1定番の構成

まず、よく見かける Web アプリケーションの構成を描きます。クラウドの特定のサービスに依存しない、一般的な形です。

この構成の要は、アプリケーションサーバーが常駐するプロセスだという点です。起動したプロセスはメモリ上に状態を持ち続け、DB への接続を張ったまま使い回します。台数を増やすときは、同じプロセスを並べてロードバランサで振り分けます。

一方、サーバーを並べると、1 台のメモリに置いた状態は他の台から見えなくなります。そこで、共有したい状態は Redis や RDB に追い出し、同じ対象への同時更新はロックで守ります。定番の構成で Redis がキャッシュと排他の 2 役を担うことが多いのは、このためです。

2Cloudflare の部品を重ねる

図 1 と同じ配置のまま、各部品を Cloudflare のサービスに置き換えると、次のようになります。

図 1 と図 2 を見比べると、変わったのは主に 2 か所です。

1 つ目は、アプリケーション層が 1 つのリージョンにまとまらず、利用者を受けたデータセンターごとに散らばることです。どこで動くかを決めるのは開発者ではなく、リクエストの到着地点です。これが次の節で扱う「エッジで動く」の意味です。

2 つ目は、アプリケーション層とデータをつなぐ線です。通常の構成では、ホスト名・ポート・パスワードを含む接続文字列を設定ファイルに書き、ネットワーク越しに接続します。Cloudflare では、設定ファイルで「この Worker は、この D1 を DB という名前で使う」と宣言し、コードからは env.DB として呼び出します。この宣言を binding と呼びます。接続先の場所も認証情報もコードには現れません。詳しくは第 1 章で扱います。

3エッジで動くということ

通常の構成では、アプリケーションサーバーを置くリージョンを 1 つ選びます。東京リージョンに置けば、東京の利用者には速く、ロンドンやサンパウロの利用者には遅くなります。光の速さで地球の裏側まで往復するだけで、100 ミリ秒以上かかるからです。

Cloudflare は、世界の 125 を超える国、330 を超える都市にデータセンター（DC）を持ち、そのすべてが同じ IP アドレスを広告しています。この方式を Anycast と呼びます。インターネットの経路制御は、同じ宛先が複数あれば近いほうへ届けるので、利用者のリクエストは自然と最寄りの DC に着きます。

そして Workers は、原則としてリクエストを受けたその DC で実行されます。どの DC でも同じコードを動かせるように、デプロイしたコードは全 DC に配られます。つまり「リージョンを選ぶ」という設定そのものがありません。この「利用者に近い場所」をエッジと呼びます。

4計算は近くに、データは 1 か所に

ここで注意が要ります。Worker が利用者の近くで動いても、データまで近くにあるとは限りません。D1 のデータベースは、書き込みを受け付ける本体（プライマリ）が 1 か所にあります。Durable Object も、最初に呼ばれた場所の近くに作られ、その後は移動しません。ロンドンで動いた Worker が東京にある DB に 3 回問い合わせれば、ロンドンと東京の往復が 3 回発生します。

この問題のために、Worker を動かす場所を変える設定が用意されています。Smart Placement は、候補となる場所ごとに処理にかかった時間を測り、バックエンドの近くで動かしたほうが明らかに速い場合にだけ、リクエストをそちらへ転送します。2026 年 1 月には、AWS などのリージョン名や接続先のホスト名を書いて、場所を明示的に指定する方法も加わりました。なお、Smart Placement はドキュメント上まだベータの扱いです。

エッジで動くことの利点がそのまま効くのは、データに触れない処理か、データが近くにある処理です。静的ファイルの配信、認証トークンの検証、リダイレクト、キャッシュから返せる応答などがこれに当たります。DB を何度も読む処理では、どこで動かすかを意識する必要があります。

5状態をどこに置くか

Worker は常駐しないので、メモリに置いた値はリクエストが終われば失われるものとして扱います。残したいものは、すべて外の保存先に書きます。保存先は 4 種類あり、通常の構成で RDB と Redis とストレージに振り分けていたものを、性質に応じて選び分けます。

図 5 で Durable Objects を D1 より先に問うているのは、「1 つの対象ごとに順に処理したい」という要求が、通常の構成ではロックや Redis を追加して初めて満たせるものだからです。Cloudflare では、この要求を満たす部品が最初から用意されていて、しかも Durable Object は自分専用の SQL のストレージを持っています。対象ごとに分けられるデータなら、D1 を使わずに Durable Objects だけで済む場合もあります。この関係は第 2 章と第 3 章で詳しく見ます。

すでに PostgreSQL や MySQL のデータベースを運用しているなら、それを使い続ける道もあります。Hyperdrive は、Worker から既存の DB への接続をプールし、読み取りをキャッシュする仕組みです。D1 に移すかどうかとは別に検討できます。

6KV：遅れて届くキャッシュ

KV はこのノートで独立した章を設けないので、ここで性質を押さえておきます。

KV は、キーと値の組を世界中から読めるストアです。本体は少数の中央のデータセンターに置かれ、各データセンターは読んだ値を一定時間キャッシュします。書き込みを全拠点に配って回るわけではなく、各拠点がキャッシュの期限が切れたときに取りに行く仕組みです。

そのため、ある場所で書いた値が他の場所で見えるようになるまで、最大で 60 秒ほど、場合によってはそれ以上かかります。「キーが存在しない」という結果もキャッシュされるので、新しく作ったキーも同じだけ遅れて見えます。公式ドキュメントは、書き込んだ場所で直後に読んだ場合でさえ、新しい値が返るとは保証していません。

さらに、同じキーへの書き込みは 1 秒に 1 回までです。カウンターのように同じキーを頻繁に更新する用途や、読んでから書き戻すまでを不可分に行いたい用途には向きません。KV は Redis のキャッシュの代わりにはなっても、Redis のロックやカウンターの代わりにはなりません。そちらは Durable Objects の仕事です。

向いているのは、設定値、機能フラグ、許可リスト、描画結果のキャッシュなど、読み取りが圧倒的に多く、更新が数十秒遅れて届いても困らないデータです。
