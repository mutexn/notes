Node.js パッケージマネージャーの社内標準

npm と pnpm を比べ、pnpm を標準にする理由と設定方法

結論

pnpm を会社標準にし、npm は例外として許可する

  • 標準：pnpm 12 系。新規案件はすべて pnpm で始める
  • 例外：npm。納品先の指定、OSS の上流、pnpm と相性の悪いツールの場合に限る
  • 移行対象：Yarn 1。Yarn 4 の既存案件は維持してよい

単一パッケージの案件だけなら、npm と pnpm の差は小さく、好みの問題に近いものです。 しかし社内にはモノレポがいくつかあり、案件数も多いため、pnpm の厳格さとモノレポ機能が効いてきます。

標準を npm と pnpm の 2 本立てにすると、設定テンプレートを 2 系統保守し続けることになります。 そのため 1 本に絞り、pnpm を選びます。

実質 npm と pnpm の 2 択である理由

候補は npm・pnpm・Bun・Yarn の 4 つです。 このうち Bun と Yarn は、社内標準にするにはエコシステムの成熟度か安定性に不安が残ります。

各ツールの現状（2026年11月）
ツール 最新版 現状
npm 12.2.2 Node.js に同梱。v12（2026年7月）で依存の install script が既定で停止になった
pnpm 12.18.0 v12 で Rust に書き直された。11 系も保守が続いている
Bun 1.4.4 1.4（2026年8月）で Rust に書き直された。パッケージマネージャー単体としての実績はまだ浅い
Yarn 4.18.1 Rust 製の Yarn 6 はリリース候補の段階。既定の PnP はツールとの相性問題が多い

Bun は速度に強みがありますが、install script に人気パッケージの既定許可リストがあり、公開直後の版を避ける設定も既定で無効です。 「何もしなくても安全」という点で pnpm に劣ります。 また、Rust 化した pnpm 12 の登場で、速度の差も縮まっています。

Bun は Bun ランタイムを採用した案件でのみ使うものとし、標準の対象からは外します。

設定を揃えたときの差

既定値どうしで比べると、npm と pnpm の差は大きく見えます。 しかし会社標準ではどちらを選んでも設定テンプレートを配るので、ここでは設定を揃えた状態で比べます。

セキュリティ：設定すればほぼ同等

npm 12 は、.npmrc に 2 行書くだけで主要な対策が揃います。

サプライチェーン対策の比較
対策 npm 12 pnpm 12
依存の install script 既定で停止。既定では警告だけで install は続く 既定で停止。未承認があると install が失敗する
公開直後の版を避ける min-release-age（日単位、既定は無効） minimumReleaseAge（分単位、既定は 1 日）
待機期間の例外 コマンド実行時の --min-release-age=0 による一時解除 パッケージ単位で設定ファイルに書ける
git / URL 依存 直接依存も含めて既定で拒否 推移依存だけ既定で拒否
署名の格下げ検知 なし trustPolicy: no-downgrade

設定を揃えたあとに残る差は、署名の格下げ検知と、待機期間の例外の指定方法です。 署名の格下げ検知は、これまで provenance 付きで公開されていたパッケージが署名なしで公開されたときに止める機能で、パッケージの乗っ取りを検知するのに効きます。

宣言していない依存を読めてしまう（幽霊依存）

npm の node_modules は依存を平らに並べるので、package.json に書いていないパッケージも import できてしまいます。 たとえば、依存の依存として入っている debug を直接使っていても動きます。

その後、上流が debug への依存をやめると、lockfile を更新したときに本番だけが壊れます。 pnpm では、このようなコードは最初から動きません。 案件数と依存の更新回数が多いほど、この差が効いてきます。

npm にも同じ構造にする install-strategy=linked がありますが、実運用での実績はまだ少ない状況です。

モノレポ機能：いちばん大きな差

モノレポ機能の比較
機能 npm pnpm
バージョンの一元管理（catalog） なし あり
依存関係をたどったフィルタ実行 なし（-w で個別に指定） --filter ...pkg など
デプロイ用の切り出し なし pnpm deploy
パッケージ間の依存の厳格さ 緩い（幽霊依存が起きる） 厳格

Turborepo や Nx を併用すれば、タスク実行の差は縮まります。 ただし、バージョンの一元管理と依存の厳格さの差は残ります。

ツール本体のバージョン固定とディスク使用量

npm のバージョンは、使っている Node.js に引きずられます。 package.json の devEngines で版を指定しても、npm は検査するだけで、正しい版に切り替えてはくれません。

pnpm は、Node.js と pnpm 自体の版を lockfile に固定し、自動で取得します。 全員と CI が同じ版を使うので、Corepack（Node.js 25 以降は同梱されていない）も nvm も要りません。

さらに pnpm は、依存をマシン全体の共有ストアに置きます。 案件が 20 個あっても、同じパッケージの実体は 1 つで済みます。

npm を選ぶ正当な理由と、例外の条件

npm の利点

  • どこにでもある：Node.js さえ入っていれば使えます。 顧客の環境、PaaS、チュートリアル、引き継ぎ先のどこでも説明が要りません。 納品や引き継ぎがある案件では、これがいちばん大きな利点です。
  • 互換性：平らな node_modules は、どのツールも前提にしている構造です。 pnpm のシンボリックリンク構造は、React Native の Metro、一部の Electron ビルダー、Lambda への zip 化、Docker での COPY などで、ときどき問題を起こします。
  • 破壊的変更が少ない：pnpm は v10 で install script を既定停止、v11 で設定ファイルを移動、v12 で Rust への書き直しと、毎年大きく変わっています。 npm はこの点で穏やかです。

運営体制にも違いがあります。 npm は GitHub が開発しており、pnpm はコミュニティ主導（中心の開発者とスポンサー）です。

それでも pnpm 1 本にする理由

「npm を標準にして、モノレポだけ pnpm」という 2 本立ても考えられますが、次のコストが継続的にかかります。

  • 設定テンプレートが 2 系統になる：.npmrc と pnpm-workspace.yaml のそれぞれでセキュリティ設定を同じ水準に保つ必要があり、片方の更新を忘れるとその案件だけ守りが弱くなる
  • 開発者が案件ごとに切り替える：コマンドも lockfile も違うので、レビューする人も両方を理解しておく必要がある
  • 単一の案件が後からモノレポになる：管理画面を足したり、共通部品を切り出したりした時点で移行作業が発生する

逆に、単一パッケージの案件で pnpm を使うコストは「各マシンに 1 回入れる」程度で済みます。 幽霊依存の防止や署名の格下げ検知は、モノレポでない案件にも効きます。

毎年の破壊的変更も、各リポジトリが devEngines で自分の版を固定するので、全案件が一斉に壊れることはありません。 案件ごとの都合に合わせて上げられます。

npm を許可する条件

  • 納品先や引き継ぎ先が npm を指定している
  • OSS に貢献するときで、上流が npm を使っている
  • pnpm と相性の悪いツールを使う（React Native など）。ただし、まず pnpm の nodeLinker: hoisted を試し、それでも解決しない場合に限る

npm を使う場合も、前述の .npmrc を必ず入れます。

モノレポとは何か

モノレポ（monorepo）は、複数のアプリやライブラリを 1 つの Git リポジトリにまとめて管理する方式です。 反対に、アプリごとにリポジトリを分ける方式をポリレポ（polyrepo）と呼びます。

パッケージマネージャーの観点では、次の 1 点で判断できます。

1 つのリポジトリに package.json が複数あり、それらが互いを依存として参照しているか

具体例

この例では、web と admin が ui を使い、api と web が types を使います。 共有するコードを npm に公開しなくても、同じリポジトリの中で import できます。 API の仕様変更と画面の修正を 1 つのプルリクエストにまとめられるのも利点です。

モノレポに当たらないもの

  • 単一のアプリ：Next.js のサイトが 1 つあるだけで、package.json も 1 つのリポジトリ
  • 言語が混在する 1 アプリ：Laravel や WordPress のテーマに Vite のフロントエンドビルドが同居しているリポジトリ。Node.js から見れば package.json は 1 つ
  • フォルダを並べただけのリポジトリ：複数の LP を置いていても、互いに参照せず、それぞれ独立に install している場合

モノリス（monolith）とは別の概念です。 モノリスは「1 つの大きなアプリ」という設計の話で、モノレポは「リポジトリをどうまとめるか」という管理の話です。

設定テンプレート

1. 各マシンに pnpm を 1 回だけ入れる

入れ方は mise、Homebrew、公式インストーラのどれでもかまいません。 プロジェクト側の指定に従って正しい版に自動で切り替わるので、手元の版を揃える必要はありません。

2. package.json

pnpm は範囲内で確定した版とチェックサムを pnpm-lock.yaml に記録し、全員がその版を使います。 Node.js は 26 が 2026年10月から Active LTS です。既存案件の 24 は 2028年4月まで使えます。

この指定があると、誤って npm install を実行しても npm が EBADDEVENGINES エラーで止まります。

3. pnpm-workspace.yaml

pnpm 11 以降、pnpm 固有の設定はこのファイルに書きます。 単一パッケージのプロジェクトでも同じです（その場合 packages は不要）。

trustPolicy は正当な理由で署名が外れた版にも反応することがあります。 その場合は trustPolicyExclude に版を指定して個別に通します。

4. .npmrc

pnpm 11 以降、.npmrc にはレジストリと認証だけを書きます。 トークンは環境変数から読み、ファイルに直接書きません。

5. 他のツールの lockfile を混ぜない

6. CI（GitHub Actions）

7. 依存の更新ツールも待機期間を揃える

Renovate か Dependabot のどちらかを使います。 待機期間は minimumReleaseAge と同じ 3 日に揃えます。

例外：npm を使う案件

前述の .npmrc を入れ、install script の承認は npm approve-scripts で管理します。 承認結果は package.json の allowScripts に記録されます。

例外：Bun ランタイムを採用した案件

install script を許可するパッケージは、package.json の trustedDependencies に明示します。

運用ルールと既存案件の移行方針

運用ルール

  • 緊急の脆弱性修正：待機期間を全体で 0 にはしない。 minimumReleaseAgeExclude にそのパッケージを一時的に入れるか、pnpm audit --fix を使う（パッチ版を自動で除外リストに入れる）
  • install script の承認：pnpm approve-builds で追加し、allowBuilds の差分をプルリクエストでレビューする
  • 社内パッケージの公開：npm の Trusted Publishing（OIDC）を使う。 2FA を経由しないトークンでの直接公開は、2027年1月ごろに廃止される予定
  • pnpm のメジャー更新：テンプレートを先に更新して検証し、各リポジトリは案件の都合に合わせて devEngines の範囲を上げる
  • 複数リポジトリへの配布：configDependencies を使うと、テンプレートの設定を社内共通パッケージにまとめて配れる

既存案件の移行方針

一斉には移行しません。効果の大きい順に進めます。

対象 方針
新規案件 最初から pnpm
既存のモノレポ 優先して移行する（効果がいちばん大きい）
既存の単一パッケージ（npm） 大きな改修や依存の更新のついでに移行する。保守だけの案件は npm のままでよい
Yarn 1 の案件 セキュリティ機能が無いので、計画的に移行する

npm workspaces のモノレポを移行する手順

  1. pnpm import で package-lock.json から pnpm-lock.yaml を作る
  2. package.json の workspaces を pnpm-workspace.yaml の packages に移す
  3. 内部パッケージへの依存を workspace:* に書き換える
  4. pnpm install を実行し、出てきたエラーを直す。 宣言漏れの依存（幽霊依存）がここで見つかるので、package.json に追加する。 作業量のほとんどはこの手順
  5. pnpm approve-builds で、install script を許可するパッケージを決める
  6. package-lock.json を削除し、CI を pnpm 用に書き換える
