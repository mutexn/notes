SMA 設計編

Cloudflare で組み立てる

チェンジセットは Durable Object に、本番はポインタ 1 つに。構想を、動く構成に落とし込む。

本編では、コード・CMS の構造・コンテンツを等しく扱う CMS として SMA（Site Management Agent）を構想し、その概念設計を示しました。このページでは、それを Cloudflare のサービスの上に具体的に組み立てます。

このページの前提は次のとおりです。

  • 実行基盤はすべて Cloudflare とする
  • 図と文章で構成を示し、コードは載せない
  • ストレージは本編の案 A と案 B の両方を扱い、どちらを選ぶべきかを示す
  • 配信は、リクエストごとに描画する方式と静的生成の両方に対応させる
  • 各サービスの提供状況と制限は、2026 年 10 月時点の公式ドキュメントに基づく

1全体構成

この構成の中心にあるのは Durable Object（DO）です。DO は名前で一意に特定でき、1 つの DO の中の処理は単一のスレッドで順に実行され、その記憶領域は強い一貫性を持ちます。チェンジセットの状態遷移や本番のポインタの付け替えを、ロックなしで矛盾なく行えるのはこの性質のおかげです。

MCP サーバーには状態を持たせません。Agents SDK で以前使われていた McpAgent は、2026 年 10 月時点で非推奨になっており、後継の createMcpHandler はリクエストごとに完結するステートレスな作りです。そこで、エージェントとのやりとりで生じる状態は、すべてチェンジセットの DO に置きます。本編の原則「エージェントにストレージを直接触らせない」は、MCP Worker がチェンジセットの DO を通してしか何もできない、という形で実現されます。

2ストレージ：小規模なら A、通常は B

案 A では、コード・スキーマ・コンテンツ・画像を 1 つの Artifacts リポジトリに置きます。チェンジセットはリポジトリの fork、公開は本流へのマージです。Git の仕組みがそのまま使えるので、作るものは最も少なく済みます。

ただし、案 A には次の課題があります。

  • 容量の上限：Artifacts は 1 リポジトリ 1 GB、1 ファイル 32 MB まで。画像を R2 に逃がしても、コンテンツの履歴はリポジトリの中で増え続ける
  • 検索：Git には索引がない。一覧や絞り込みのたびにリポジトリを読むか、別に索引を作ることになる。D1 に索引を持つなら、構成は案 B に近づく
  • 反映の速さ：コンテンツだけの変更でも、公開にはビルドとデプロイが要る。Workers Builds のビルドは 1 回 20 分まで
  • 権限の粒度：Artifacts のトークンは、リポジトリ単位で読み取りか書き込みかを分けるだけ。フィールド単位の権限は、SMA コアがファイルの差分を解釈して判定するしかない

目安として、ページ数が数百程度までで、更新が 1 日に数回までなら、案 A で始められます。それを超える場合、そして多くのサイトの運用では、案 B を推奨します。案 B では、Git が得意なコードとスキーマだけを Artifacts に置き、コンテンツは件数・検索・即時反映に強い仕組みに置きます。どちらを選んでも SMA コアから上は変わらないので、案 A で始めて案 B へ移ることもできます。

以降は案 B を前提に書き、案 A と違う点だけを補います。

3コンテンツストア

  • コレクションごとに 1 つの DO：記事・FAQ・お知らせといったコレクションごとに DO を分ける。SQLite を使う DO は 1 つあたり 10 GB まで保存できる。それを超えそうなコレクションは、さらにキーの範囲で分割する
  • リビジョンは追記のみ：公開前のチェンジセットで作った版も、同じ DO にリビジョンとして書く。マニフェストは公開に使う時点で凍結し、ID で参照する
  • チェンジセットは差分だけ：チェンジセットの DO が持つのは、土台のマニフェストの ID と、変えたエントリの対応だけ。分岐のコストは、変えたエントリの数にしか比例しない
  • 索引は D1：D1 には本流のマニフェストの索引を持つ。チェンジセットの中での検索は、D1 の結果にチェンジセットの差分を重ねて返す
  • 画像は R2：画像は内容のハッシュをキーにして R2 に置き、リビジョンからはキーで参照する。R2 の条件付き書き込みを使えば、同じキーの上書きを防げる

通常の巻き戻しは、後で述べるリリースの付け替えで行います。それとは別に、SQLite を使う DO には過去 30 日の任意の時点へ戻す機能（point-in-time recovery）があり、データそのものが壊れたときの最後の備えになります。

4エージェントの接続と権限

  • 誰の指示かを最初に確定する：人間の認証は Access で行う。エージェントは MCP の OAuth で接続し、認可サーバーには Access を使う（workers-oauth-provider が Access との連携に対応している）。これで、すべての操作が特定の人間の指示に結びつく
  • ケイパビリティはチェンジセットの DO が発行する：中身は、対象のチェンジセット・層・対象（コードならパス、コンテンツなら型とフィールド）・操作・期限。MCP のツールは、呼び出しのたびにチェンジセットの DO に可否を問い合わせる
  • コードだけは git で直接書かせる：コーディングを得意とするエージェントは、git で作業するのがいちばん効率がよい。そこで、そのチェンジセットの fork にだけ書ける、期限つきのトークンを渡す。本流のリポジトリに書けるトークンは、SMA コアだけが持つ。fork は隔離された複製なので、Cloudflare OS の Gadget と同じく、その中では自由に変えてよい
  • 読んだものを記録する：エージェントが読んだエントリを、機密の区分とともにチェンジセットの DO に記録する。予約公開前のエントリを読んだチェンジセットでは、公開中のページへの書き込みを止める

5チェンジセットの一生

チェンジセットを作ると、専用の DO と、コードとスキーマの fork ができます。エージェントがレビューに出すと、Workflows のインスタンスが起動し、検証・プレビューの用意・承認待ち・公開を順に進めます。各段階は Workflows のステップとして実行されるので、途中で失敗しても再試行され、どこまで進んだかが失われません。

承認待ちには、Workflows の waitForEvent を使います。外部からのイベントを待つ機能で、待てる期間は 1 秒から 365 日まで設定できます（既定は 24 時間）。管理画面で人間が承認すると、そのインスタンスにイベントが送られ、公開へ進みます。複数のチェンジセットをまとめて承認するのは、複数のインスタンスにイベントを送ることにあたります。待機中のインスタンスは同時実行数の上限に数えられないので、承認待ちが溜まっても実行枠を圧迫しません。期限が切れたら、差し戻しとして扱います。

承認を待つ間も、エージェントは次のチェンジセットを、承認待ちのチェンジセットを土台にして作れます。土台が却下されたら、その上に積んだチェンジセットも作り直しの対象になります。

状態の遷移は、すべて監査ログとして R2 に追記します。R2 のバケットロックを使えば、決めた期間は記録を削除も上書きもできなくなります。なお、Workers Analytics Engine は書き込みと照会の両方でサンプリングされ、個々の記録を必ず取り出せるとは限らないため、監査ログには向きません。

6検証とプレビュー

  • ビルドと検証：Workers Builds が fork のコードをビルドする（Artifacts との連携に対応している）。検証は Sandbox で行う。コンテンツがスキーマに合っているか、コンポーネントが存在するフィールドだけを読んでいるか、リンク切れやアクセシビリティの問題がないかを調べ、サイトグラフも計算し直す
  • 版を登録するだけで、デプロイはしない：Workers には、本番に出さずに新しい版だけを登録する仕組みがある。登録した版にはチェンジセット専用の別名をつけ、その別名の Version URL をプレビューに使う。Version URL は既定で誰でも開けるので、Access で保護する
  • 候補のコンテンツを解決する：フロントエンドは、開かれたホスト名（別名）をコンテンツ API に伝える。コンテンツ API はそこからチェンジセットを特定し、土台のマニフェストに差分を重ねた候補のコンテンツを返す

ここに 1 つ、構成を左右する制約があります。Version URL は、Durable Objects を使う Worker では使えません。そのため、フロントエンドの Worker には DO を直接バインドせず、コンテンツは service binding でつないだコンテンツ API の Worker から取ります。この分離は、後で述べるロールバックの制約を避けるうえでも役に立ちます。

静的生成の場合は、候補のマニフェストでビルドした静的アセットを含む版を登録し、同じく Version URL で確認します。

7公開

承認されたチェンジセットは、Workflows の手順として次の順に公開します。

  1. スキーマを拡張する：fork のスキーマの変更のうち、追加の部分だけを本流にマージする（s2）
  2. コンテンツを移行する：コレクションの DO に移行後のリビジョンを書き、マニフェストを凍結して、リリース DO を付け替える（R2）
  3. コードをデプロイする：新しいコードの版をデプロイする（v2）。新旧どちらのコードも R2 の上で動くことは、1 と 2 で保証されている。そのため、段階的デプロイで新しい版への割合を少しずつ上げてもよい
  4. 新しいコンテンツを公開する：チェンジセットのエントリを含むマニフェストを凍結し、付け替える（R3）
  5. スキーマを縮小する：どこからも参照されていないことを D1 のサイトグラフで確かめてから、古いフィールドを本流から削除する（s3）

途中の段階で失敗したら、それまでの段階を逆順に戻します。リリース DO は、リリースごとにコードの版・スキーマのコミット・マニフェストの組を記録しておき、どのリリースにも確実に戻れるようにします。

Workers のロールバックには制約があります。戻せるのは直近 100 版までで、間に Durable Object のクラス構成の変更などが挟まると戻せません。フロントエンドの Worker に DO を持たせない構成は、この制約を受けにくくするためでもあります。

8配信：2 つの方式

リクエストごとに描画する場合

フロントエンドの Worker は、まずリリース DO に現在のリリースを問い合わせ、次にそのリリースを指定してコンテンツ API から中身を取ります。リリースが指すマニフェストは凍結されていて中身が変わらないので、キャッシュのキーにリリースの ID を含めれば、キャッシュを消す必要がそもそもなくなります。Workers の Cache API はデータセンターごとに独立していて、削除もそのデータセンターにしか効きません。しかし、キーが変わらない中身だけを指すなら、この性質は問題になりません。

リクエストのたびに、全体で 1 つのリリース DO へ問い合わせるのは負荷が集中します。そこで、現在のリリースの ID は、各データセンターで数秒だけキャッシュします。その代わり、公開が反映されるまでに数秒の遅れが出ます。

静的生成の場合

静的生成では、Workers のデプロイそのものが本番のポインタになります。公開のたびに、凍結したマニフェストでビルドし、静的アセットを含む版を登録してデプロイします。巻き戻しは Workers のロールバックで行います。ただし、コンテンツの公開が多いと、直近 100 版というロールバックの範囲をすぐに使い切ります。リリース DO にコードのコミットとマニフェストの組を残しておけば、範囲を過ぎた古いリリースも、ビルドし直して戻せます。

どちらの方式でも、リリースという考え方と、公開・巻き戻しの手順は変わりません。違うのは、本番のポインタをリリース DO に置くか、Workers のデプロイに置くかだけです。

9並行制御

公開の受け付けは、リリース DO が 1 件ずつ直列に処理します。DO の単一スレッドの性質により、リリース DO はそのままマージの順番待ちの列として働きます。

自分の番が来たチェンジセットは、次の順に調べられます。

  1. コード：fork を、現在の本流に 3-way でマージできるかを Sandbox で確かめる
  2. コンテンツ：チェンジセットの差分を、現在の本流のマニフェストとエントリ単位で比べる
  3. 意味上の競合：このチェンジセットが変えた要素と、土台の時点より後に公開された変更とが、D1 のサイトグラフ上で依存関係によって結ばれていないかを照会する

競合が見つかったら、エージェントに、新しい本流の上でチェンジセットを作り直すよう求めます。本編で述べたとおり、エージェントにとって作り直しは安い作業なので、複雑な自動マージには頼りません。

10残る課題

  • サービスの成熟度：Artifacts は 2026 年 10 月 1 日にオープンベータになったばかりで、Workers の有料プランが前提になる。D1 のリードレプリカや Dynamic Workers もベータ版。本番で採用する前に、最新の状態を確かめる必要がある
  • リリース DO への集中：全体で 1 つの DO に、公開と現在の版の問い合わせが集まる。数秒のキャッシュで足りない規模では、読み取りを分散する仕組みが要る
  • コレクションの分割：10 GB を超えるコレクションをどう分割し、分割をまたぐ参照をどう扱うかは、まだ設計していない
  • 人間の同時編集：同じチェンジセットを複数の編集者がリアルタイムに編集する仕組みは、ここでは扱っていない
  • 候補のコードを隔離して動かす別の方法：Version URL の代わりに、Cloudflare OS の Gadget と同じく Dynamic Workers で候補のコードを隔離して動かせば、DO を使えないという制約や、別名の数（直近 1,000 件まで）から離れられる可能性がある。ただし、まだ検証していない
