SMA 構想

AI 時代の CMS は、サイトを管理するエージェントになる

コードも、CMS の構造も、コンテンツも。AI への 1 つの指示で、すべてを変えられるようにする。

ヘッドレス CMS は、コンテンツをコードから切り離すことで成功しました。しかし AI エージェントがサイトの運用を担うようになると、その分離が今度は足かせになります。このページでは、ヘッドレス CMS が何を解決し、どんな前提の上に立っているかを振り返ったうえで、AI 時代の CMS の理想像を提言します。

序「FAQ を追加して」という一文

サイトの運営者が、AI にこう頼んだとします。「トップページに、よくある質問のセクションを追加して」。

指示は一文です。しかしヘッドレス CMS で構築したサイトでこれを実現するには、性質の異なる 3 つの変更が必要になります。

  1. コード：FAQ を表示するコンポーネントを実装し、トップページに配置する。変更先は Git リポジトリ
  2. CMS の構造：「質問」と「回答」をもつ FAQ 型をスキーマに定義し、トップページの型から参照できるようにする。変更先は CMS の管理画面か、スキーマ定義ファイル
  3. コンテンツ：質問と回答を実際に入力し、公開する。変更先は CMS の編集画面

今のヘッドレス CMS では、この 3 つは置き場所も、変更できる人も、本番に反映する手順も別々です。AI がどれほど賢くなっても、3 つの場所をまたいで整合性を取りながら作業する負担は残ります。

このページでは、コードもコンテンツの一部と見なし、AI への指示によってコード・CMS の構造・コンテンツをまとめて変更できる CMS を構想します。その名前を SMA（Site Management Agent）としました。

遠回りに見えますが、まずはヘッドレス CMS が何を解決したのかから振り返ります。理想像を描くには、今の仕組みがどんな前提の上に立っているかを知る必要があるからです。

第1章ヘッドレス CMS は従来型 CMS の何を解決したのか

従来型 CMS：表示とデータが一体だった

WordPress に代表される従来型 CMS は、コンテンツの保存・編集画面・HTML の生成を、ひとつのアプリケーションで担います。記事はデータベースに入り、リクエストのたびに PHP のテーマがそれを読み出して HTML を組み立てる。編集者が管理画面で「公開」を押せば、その瞬間からサイトに反映されます。

この一体性は、導入しやすいという大きな利点でした。けれどサイトの規模や用途が広がるにつれて、次のような限界が目立つようになります。

  • フロントエンドの技術が縛られる。表示はテーマ（PHP のテンプレート）で書く前提で、React などのモダンなフロントエンド技術を素直に使えない
  • Web 以外へ配信しにくい。コンテンツが HTML の生成と結びついているため、スマートフォンアプリなど他のチャネルで同じコンテンツを使い回しにくい
  • 性能とセキュリティの負担が大きい。リクエストごとの動的生成はキャッシュの工夫なしには遅く、公開サーバー上の管理画面やプラグインは攻撃の入口になりやすい

ヘッドレス CMS：コンテンツを API として切り出した

ヘッドレス CMS は、この一体構造から「頭」、つまり表示層を切り落としました。CMS が受け持つのは、コンテンツの構造定義・編集・保存だけです。コンテンツは API を通じて JSON などの形で取り出され、HTML をどう組み立てるかは CMS の外にあるフロントエンドが決めます。

この分離によって、3 つの限界はそれぞれ解消されました。

  • フロントエンドを自由に選べる。Next.js でも Astro でもネイティブアプリでも、API を読めれば何でもよい
  • 複数のチャネルに配信できる。同じコンテンツを Web とアプリに同時に届けられる
  • 静的生成と CDN 配信を組み合わせられる。ビルド時に HTML を生成して CDN から配る Jamstack の構成と相性がよく、管理画面を公開サーバーから切り離せる

この流れをもっと詳しく

WordPress の時代から Jamstack、Next.js に至る経緯は、Jamstackと、その先のWeb と Web技術開発史 で扱っています。

本質は関心の分離

技術的な利点を並べましたが、ヘッドレス CMS が成し遂げたことを一言でまとめるなら、関心の分離です。コンテンツは編集者が CMS で管理し、コードは開発者が Git で管理する。両者は API という契約を挟んで、互いの領分に踏み込まずに仕事を進められるようになりました。

この分離は、人間どうしの分業として非常にうまく機能しています。ただし、うまく機能しているのは、ある前提が成り立っているからです。

第2章ヘッドレス CMS の前提

ヘッドレス CMS の設計には、明文化されていない前提がいくつも含まれています。ここでは 4 つを取り出します。

前提 1　変更する主体は、役割の分かれた人間である

ヘッドレス CMS が想定する利用者は、開発者と編集者の 2 種類です。開発者はスキーマを定義し、フロントエンドを実装する。編集者は、用意されたフォームにコンテンツを入力する。管理画面の権限設計も、この 2 つの役割を基本に組み立てられています。

裏を返せば、編集者がレイアウトを変えたいと思ったら、開発者に依頼するしかありません。それは制約であると同時に、コードの品質を守るための防波堤でもありました。

前提 2　層ごとに変更の頻度が違う

コード・CMS の構造・コンテンツの 3 層は、変わる頻度が大きく異なります。コンテンツは毎日のように更新されますが、スキーマやコンポーネントが変わるのは、リニューアルや機能追加のときくらいです。

だからこそ、「開発者が型を作り、編集者がその型を埋める」という分担が成り立ちます。型は滅多に変わらない土台で、その上でコンテンツだけが頻繁に動く。スキーマの変更は、開発者が計画的に行う特別なイベントとして扱われます。

前提 3　層ごとに別のシステムで管理する

3 層は、それぞれ別のシステムに住んでいます。コードは Git リポジトリにあり、変更はプルリクエストでレビューされ、CI/CD でデプロイされます。コンテンツは CMS のデータベースにあり、下書き・公開・版の履歴は CMS 独自の仕組みで管理されます。スキーマはその中間で、CMS の管理画面で定義する製品もあれば、コードとして Git に置く製品もあります。

変更の履歴も、レビューの手順も、本番への反映も、層ごとに別々です。序の FAQ の例では、スキーマの更新、コンポーネントのデプロイ、コンテンツの公開という 3 つの手順を、正しい順序で行う必要があります。順序を誤れば、存在しないフィールドを参照してビルドが壊れたり、表示先のないコンテンツが公開されたりします。

層をまたぐ整合性は、システムではなく人間どうしの調整で保たれています。チケットで依頼し、リリース日を合わせ、手順書に従う。それで回るのは、前提 1 と前提 2 が成り立っているからです。

前提 4　変更は人間の速度で起こる

最後の前提は、変更の速度と量です。人間が手で行う変更は 1 日に数件から数十件程度で、同じ箇所を複数人が同時に触ることは多くありません。CMS の同時編集対策が、下書きの分離や編集ロック程度で足りているのはそのためです。

第3章AI 時代における運用の前提

AI、とりわけ指示を受けて自律的に作業を進めるエージェントが運用に加わると、前章の 4 つの前提はそれぞれ崩れます。

変更の主体がエージェントになる

運営者や編集者は、変更を自分の手で行うのではなく、AI に自然言語で指示するようになります。そして自然言語の指示は、層の区別を気にしません。

「FAQ を追加して」は、コード・構造・コンテンツの 3 層にまたがります。「この見出しをもう少し目立たせて」は編集者の言葉としては自然ですが、実際にはスタイルの変更、つまりコードの変更です。開発者と編集者という役割の境界は、指示を実行するエージェントの側で溶けてしまいます。

層ごとの頻度の差が縮む

エージェントがコードを書けるようになると、コードを変更するコストは大きく下がります。新しいセクションのためにコンポーネントを作ることが、記事を 1 本書くのと同じくらいの手間でできるなら、コードとスキーマもコンテンツと同じ頻度で変わり始めます。

「型は滅多に変わらない土台」という前提がなくなれば、スキーマの変更を特別なイベントとして扱う運用は、日常の足かせになります。

層の分断が障害になる

人間にとって、3 つのシステムを行き来するのは面倒ではあっても、我慢できる手間でした。エージェントにとっては事情が違います。Git と CMS で別々の認証・API・変更履歴を扱い、デプロイと公開の順序を合わせ、途中で失敗したら層ごとに巻き戻す。変更の頻度が上がるほど、この分断は失敗の温床になります。

人間のレビューも難しくなります。1 つの指示から生じた変更が Git のプルリクエストと CMS の下書きに分かれていては、レビュアーは「この指示に対して何が変わったのか」を一望できません。

変更が並行して大量に起こる

エージェントは 1 体とは限りません。翻訳、SEO の改善、アクセシビリティの修正、デザインの調整をそれぞれ担うエージェントが、同時に同じサイトへ変更を加えることが考えられます。

変更の量は人間の速度を大きく超え、同じページや同じスキーマに複数の変更が重なることが日常になります。人間の役割は、変更を自分で行うことから、エージェントの変更をレビューし、承認することへ移っていきます。

コードも、コンテンツと見なす

4 つの前提が崩れた後に残る結論は、ひとつです。コードを、コンテンツとは別の世界に置いておく理由がなくなります。

ヘッドレス CMS はコンテンツを API として切り出し、コードから分離しました。AI 時代の CMS に必要なのは、分離した層をもう一度ひとつの管理下に置き、コードもスキーマもコンテンツも、同じように編集・レビュー・公開できる対象として扱うことです。

これは従来型 CMS への逆戻りではありません。表示とデータの結合を戻すのではなく、分離した層を「変更の管理」という面でだけ束ね直す、という意味です。フロントエンドの自由も、複数チャネルへの配信も、静的生成も手放さずに済みます。

第4章SMA から見た、いまのヘッドレス CMS の課題

第3章で見た前提の変化を、いまのヘッドレス CMS に当てはめてみます。エージェントが 3 層をまとめて変更する運用を前提にすると、7 つの課題が浮かび上がります。

ここで挙げるのは特定の製品の欠点ではなく、ヘッドレス CMS という設計が共通して抱えがちな傾向です。製品によっては、一部を補う機能を備えているものもあります。

課題 1　変更をまとめる単位がない

ヘッドレス CMS の版の管理は、基本的にエントリ単位です。記事 1 本、FAQ の 1 項目といった単位で下書きと公開を繰り返します。そのため、1 つの指示から生じた複数の変更を、ひとまとまりとして扱えません。

複数の変更を束ねて同時に公開するリリース機能を持つ製品もあります。ただし、束ねられるのはコンテンツだけで、コードのデプロイとは連動しません。

課題 2　コードとの間にトランザクションがない

CMS の公開とコードのデプロイは、Webhook などで片方向につながっているだけです。CMS でコンテンツを公開するとビルドが走る、という連携はできても、「スキーマを更新し、コードをデプロイし、コンテンツを公開する」という一連の手順を、順序を保証して実行する仕組みはありません。

途中で失敗したときも同じです。ビルドが壊れたらコードを戻し、CMS の変更も手で戻す。一括で巻き戻す手段がないので、層ごとに後始末をすることになります。

課題 3　プレビューにコード変更を含められない

ヘッドレス CMS のプレビューは、本番と同じコードの上で、コンテンツの下書きを表示する仕組みです。コンテンツだけを変えるなら、これで足ります。

しかし FAQ の例のように新しいコンポーネントが必要な変更では、未デプロイのコードと新しいコンテンツを組み合わせた姿を見なければなりません。そのためには、コードのプレビュー環境を別に用意し、CMS の下書きと手で結びつける必要があります。

課題 4　スキーマの変更とコンテンツの移行が分かれている

スキーマを管理画面で編集する製品では、スキーマの変更がコードと一緒に版管理されません。いつ誰がどのフィールドを変えたのかを、コードの変更と突き合わせて追うのが難しくなります。

既存のコンテンツを新しいスキーマに合わせて変換する移行ツールを提供している製品もあります。それでも、移行はスキーマの変更とは別の手順として実行するのが一般的です。スキーマだけ変わって移行が漏れる、という事故の余地が残ります。

課題 5　ブランチと競合検出が弱い

開発用・検証用に、コンテンツやスキーマの環境を丸ごと複製する機能を持つ製品はあります。しかしこれは、Git のブランチのように変更ごとに作業領域を切り、後で本流に統合するための仕組みではありません。

複数のエージェントがそれぞれの作業領域で変更し、公開前に層をまたいで競合を検出してマージする。こうした使い方は、いまのヘッドレス CMS では想定されていません。

課題 6　権限が人間の役割を前提にしている

権限の設計は、管理者・開発者・編集者といった人間の役割を単位に組み立てられています。外部から操作するための API トークンも、読み取り専用か、管理操作をすべて許すか、といった粗い粒度で発行されることが多くあります。

これでは、「翻訳エージェントは翻訳フィールドだけを変更できる」といった細かな限定がしにくくなります。また、変更の記録に残るのはトークンの持ち主で、「誰の指示で、どのエージェントが変えたか」までは辿れません。

課題 7　スキーマとコンポーネントの対応が暗黙になっている

どの型をどのコンポーネントで表示するのかという対応関係は、フロントエンドのコードの中にしかありません。CMS はスキーマを知っていても、それがサイトのどこにどう表示されるのかを知りません。

エージェントがスキーマを変更するとき、影響を受けるコンポーネントやページを知るには、コードを読み解いて推測するしかありません。

課題は、前提から生まれている

7 つの課題は、どれも第2章で見た前提から自然に生まれたものです。役割の分かれた人間が、層ごとに別のシステムで、人間の速度で変更する。その前提のもとでは合理的だった設計が、エージェントによる運用では障害になります。

次の章では、これらの課題を解消するために、SMA が備えるべき性質を提言します。

第5章提言：コード・構造・コンテンツを等しく扱う

以上を踏まえて、SMA に求められる性質を 5 つ提言します。

提言 1　3 層を 1 つの変更単位で扱う

1 つの指示から生じた変更は、層をまたいでいても 1 つのまとまり、つまりチェンジセットとして扱えるべきです。FAQ の例なら、コンポーネントの追加・スキーマの追加・コンテンツの入力が 1 つのチェンジセットに入ります。

チェンジセットは、まとめてプレビューし、まとめてレビューし、まとめて公開し、問題があればまとめて巻き戻せる必要があります。Git のプルリクエストに近い発想ですが、その対象をコードだけでなく、CMS の構造とコンテンツにまで広げるということです。スキーマ、コード、コンテンツといった公開の順序も、人間の手順書ではなくシステムが保証します。

提言 2　スキーマの変更とコンテンツの移行をセットにする

スキーマが頻繁に変わる以上、既存のコンテンツをどう追従させるかが問題になります。フィールドを改名したら既存の値を新しいフィールドへ移し、1 つのフィールドを 2 つに分けたら既存の値を分割する。こうしたコンテンツの移行（マイグレーション）は、スキーマの変更と同じチェンジセットに含め、プレビューの段階で移行後の姿を確認できるべきです。

データベースのマイグレーションがアプリケーションのコードと一緒に管理されるのと同じように、CMS のスキーマとコンテンツも一緒に進化させます。

提言 3　複数のエージェントを前提に並行制御する

複数のエージェントが同時に作業するなら、それぞれが独立した作業領域（ブランチ）を持ち、互いの途中経過に干渉しない必要があります。そして公開の前には、層をまたいで競合を検出しなければなりません。

競合は、同じ行を書き換えたという単純なものだけではありません。翻訳エージェントが訳し終えた直後に、別のエージェントが原文の見出しを変えた。あるエージェントが削除したフィールドを、別のエージェントが入力したコンテンツが使っていた。こうした意味の上での食い違いも、検出の対象にする必要があります。

提言 4　権限・承認・監査を備える

エージェントに何でも変えさせてよいわけではありません。エージェントごとに、変更できる範囲を限るべきです。たとえば翻訳エージェントはコンテンツの翻訳フィールドだけ、デザイン調整のエージェントはスタイルに関わるコードだけ、というように、層と対象を組み合わせて権限を定義します。

公開の前には、人間の承認を挟めるようにします。どの変更に承認を必須とするかは、影響の大きさに応じて設定できるとよいでしょう。誤字の修正は自動で公開し、スキーマの変更は必ず人間が確認する、といった具合です。

そして、すべての変更について「誰の指示で、どのエージェントが、何を変えたか」を記録に残します。人間が手を動かさなくなるほど、変更の経緯を後から辿れることが運用の信頼性を支えます。

提言 5　サイトの構造を機械が読める形で持つ

エージェントが 3 層を正しく変更するには、サイトの構造を理解できなければなりません。どのスキーマがどのコンポーネントで表示されるのか、どのページがどのコンテンツを参照しているのか、デザインの規約や文体の決まりは何か。こうした知識が人間の頭の中や散らばったドキュメントにしかなければ、エージェントは推測で作業することになります。

SMA は、サイトの構造と規約を、エージェントが問い合わせられる形で持つべきです。MCP（Model Context Protocol）のような、AI がツールやデータにアクセスするための標準的な接続方式を通じて公開すれば、特定の AI に縛られずに済みます。

第6章SMA の設計

第5章の提言を、どのような部品で組み立てるか。この章では SMA の概念設計を示します。特定の製品や実装方式は前提にせず、部品の役割と、部品どうしの関係に焦点を当てます。

全体構成

設計の中心にある原則は、エージェントにストレージを直接触らせないことです。エージェントは MCP を通じて SMA コアに変更を提案するだけで、Git リポジトリやコンテンツのデータベースに直接書き込むことも、本番に公開することもできません。すべての変更が SMA コアを通るので、権限の確認・チェンジセットへの記録・監査ログへの書き込みを、1 か所で漏れなく強制できます。

SMA コアは、次の 4 つの部品で構成します。

  • チェンジセット管理：1 つの指示から生じた 3 層の変更を 1 つの単位として保持し、その状態を管理する
  • ポリシーと承認：エージェントごとに許された操作かを判定し、公開に必要な承認を決める
  • サイトグラフ：ページ・コンポーネント・型・フィールド・エントリの依存関係を保持する
  • 監査ログ：誰の指示で、どのエージェントが、何を変えたかを記録する

承認されたチェンジセットは、公開パイプラインに渡ります。パイプラインは検証とプレビューを経て、決められた順序で 3 層を段階的に本番へ反映します。

先行事例：Cloudflare OS の Gadget と Gatekeeper

SMA の設計を考えるうえで、大きなヒントになる先行事例があります。Cloudflare が 2026 年 8 月にオープンソースで公開した Cloudflare OS です。社員一人ひとりにエージェントを与え、文書やアプリを作らせ、社内のシステムにつなぐための基盤で、CMS ではありません。それでも、エージェントに安全に変更をさせるための仕組みは、SMA が解くべき問題とよく似ています。

Gadget は、エージェントが作るアプリの単位です。アプリは利用者ごとの私的なインスタンスとして、隔離されたサンドボックスで動き、状態は Durable Object が持ちます。隔離されているので、利用者は足りない機能をエージェントに頼み、そのアプリのコードに足してもらえます。コードとデータがひとまとまりになり、どちらも気軽に変えられる対象になっている点は、「コードもコンテンツと見なす」という本稿の主張の実例といえます。

Gatekeeper は、Gadget やエージェントと外部サービスとの間に立つ、サービスごとの仲介役です。資格情報を自分で持ってエージェントには渡さず、特定のリソースだけへのアクセスを許し、すべての操作を記録します。エージェントは何の権限も持たない状態から始まり、必要なリソースへのアクセスを個別に要求します。

特に示唆的なのは、承認の扱いです。承認が必要な操作に出会うと、Gatekeeper は結果をシミュレートしてエージェントに作業を続けさせ、操作をキューに積みます。人間は後から、まとめてでも 1 件ずつでも承認できます。さらに Gatekeeper は、エージェントが何を読んだかを記録し、それに応じてその後に許す操作を決めます。

言い換えれば、SMA コアは、Git とコンテンツストアに対する Gatekeeper です。

チェンジセット

チェンジセットは、SMA における変更の最小単位です。1 つのチェンジセットは次の情報を持ちます。

  • 指示：誰が、どんな言葉で依頼したか
  • 担当エージェント：どのエージェントが変更を作ったか
  • 層ごとの差分：コードの差分、スキーマの差分、コンテンツの差分
  • 移行の手順：スキーマの変更に伴って、既存のコンテンツをどう変換するか
  • 状態：いまどの段階にあるか

チェンジセットは、次の順に状態を進めます。

  1. 作成：エージェントがチェンジセットを開き、変更を積み上げる
  2. 検証：ビルド、型の整合性（コンテンツがスキーマに合っているか、コンポーネントが存在するフィールドだけを読んでいるか）、リンク切れやアクセシビリティを自動で確かめる。失敗したら、理由を添えてエージェントに差し戻す
  3. レビュー：プレビュー環境で、3 層の変更を合わせた姿を確認できるようにする
  4. 承認：ポリシーが求める承認を得る。自動で承認されるものもあれば、人間の確認が必須のものもある
  5. 公開：公開パイプラインが、決められた順序で本番に反映する

承認を待つ間、エージェントの手を止める必要はありません。承認待ちのチェンジセットの上に、次のチェンジセットを積み重ねられるようにします。Gatekeeper が操作の結果をシミュレートしてエージェントに作業を続けさせるのと同じ考え方です。土台のチェンジセットが差し戻されたら、その上に積んだチェンジセットも作り直しの対象になります。

公開後に問題が見つかったときは、変更を打ち消す逆向きのチェンジセットを作って巻き戻します。履歴を消して元に戻すのではなく、巻き戻しも 1 つの変更として記録に残すためです。

公開の順序

3 層を一度に切り替えようとすると、どこかで「新しいコードが古いスキーマを読む」ような瞬間が生まれます。そこで SMA は、データベースの移行でよく使われる expand/contract パターンに従い、スキーマを拡張してから縮小する順序で公開します。

  1. スキーマを拡張する：新しいフィールドを追加する。古いフィールドは残しておく
  2. コンテンツを移行する：既存の値を、新しいフィールドへ写す
  3. コードをデプロイする：新しいフィールドを読む表示に切り替える
  4. 新しいコンテンツを公開する：チェンジセットで追加・変更したコンテンツを公開する
  5. スキーマを縮小する：どこからも参照されなくなった古いフィールドを削除する。参照が残っていないことは、サイトグラフで確かめる

各段階の終わりで、サイトは常に正しく動く状態にあります。途中の段階で失敗しても、それまでの段階を逆順に戻せば、公開前の状態に復帰できます。人間が手順書で守っていた順序を、システムが保証するということです。

サイトグラフ

サイトグラフは、サイトを構成する要素とその依存関係を表すグラフです。ノードはページ・コンポーネント・型・フィールド・エントリで、エッジは「このページはこのコンポーネントを使う」「このコンポーネントはこのフィールドを読む」「このエントリはあのエントリの翻訳である」といった関係です。

グラフは、次の 3 つの情報源から組み立てます。

  • スキーマの定義：型とフィールド、型どうしの参照
  • コードの静的解析：どのコンポーネントが、どの型のどのフィールドを読んでいるか
  • コンテンツの参照：どのエントリが、どのエントリを参照しているか

静的解析では、動的に組み立てられた参照を拾いきれないことがあります。そのため、コンポーネントが読むフィールドを宣言する規約を設け、解析と宣言の両方からグラフを作るのが現実的です。宣言と実際の読み取りが食い違えば、検証の段階で検出できます。

サイトグラフには 3 つの使い道があります。変更の影響範囲を求めること、後で述べる意味上の競合を検出すること、そしてエージェントに作業の文脈を与えることです。

並行制御

チェンジセットは、作成した時点の本流のスナップショットから分岐した作業領域を持ちます。複数のエージェントは、互いの途中経過を見ることなく、それぞれの作業領域で変更を進めます。

公開の前には、本流との統合を行います。統合は 2 段階です。

  1. 層ごとのマージ：コードは行単位の 3-way マージ、スキーマはフィールド単位、コンテンツはエントリとフィールド単位でマージする。同じ箇所を両方が変えていれば、構文上の競合になる
  2. 意味上の競合の検出：2 つのチェンジセットが変えた要素が、サイトグラフ上で依存関係によって結ばれていれば、競合の候補とする。原文の見出しの変更と、その見出しの翻訳。フィールドの削除と、そのフィールドへの入力。こうした組み合わせは、行が重ならなくても衝突している

競合が見つかったら、後から公開しようとしたチェンジセットを差し戻し、新しい本流の上で作り直すようエージェントに求めます。人間にとってマージの作り直しは重い作業ですが、エージェントにとっては安い作業です。複雑な自動マージに頼るより、差し戻して作り直すほうが単純で、結果も確かめやすくなります。

権限と監査

ポリシーは、「どのエージェントが」「どの層の」「どの対象に」「どの操作を」してよいかの組み合わせで定義します。対象は、コードならファイルのパス、スキーマなら型、コンテンツなら型とフィールドで指定します。翻訳エージェントには、コンテンツの翻訳フィールドへの書き込みだけを許す、といった具合です。

エージェントに渡すのは、Git やコンテンツストアの API トークンではありません。「このチェンジセットの中で、この型のこのフィールドを書き換えてよい」という、対象を限った権限（ケイパビリティ）です。資格情報そのものは、SMA コアだけが持ちます。

承認のルールも、チェンジセットの中身から決めます。コンテンツの軽微な修正だけなら自動で承認し、スキーマの縮小を含むなら人間の承認を必須にする。ルールは、変更の種類と影響範囲（サイトグラフから求める）を条件に書けるようにします。

判定には、エージェントが何を読んだかも使います。予約公開前の発表や社外秘の下書きを読んだエージェントには、公開中のページへの書き込みを許さない。Cloudflare OS の Gatekeeper が、エージェントの見たものに応じて方針を変えるのと同じ考え方です。

ここで重要なのは、ポリシー自体もチェンジセットで変更することです。ポリシーの変更には常に人間の承認を必須にしておけば、エージェントが自分の権限を自分で広げることはできません。

監査ログは追記専用とし、指示・チェンジセット・承認・公開を互いに結びつけて記録します。本番のある変更から、それを生んだ指示まで、いつでも辿れるようにするためです。

エージェント向けのインターフェース

SMA コアは、MCP サーバーとしてエージェントに機能を公開します。公開する機能は、読む機能と書く機能に分かれます。

  • 読む機能：サイトグラフの照会、スキーマとコンテンツの取得、変更の影響範囲の取得
  • 書く機能：チェンジセットを開く、コード・スキーマ・コンテンツの変更を加える、プレビューを依頼する、レビューに出す
  • 参照資料：デザインの規約、文体のガイド、用語集など、エージェントが判断の拠り所にする文書

書く機能は、すべてチェンジセットの中でしか働きません。そして、公開する機能はエージェントに与えません。公開は、承認を経た公開パイプラインだけが行います。

第7章ストレージの設計

第6章の部品は、どれもストレージの上に載っています。この章では、3 層のデータをどこに、どのような形で保存するかを考えます。

2 つの案

3 層のデータをどこに保存するかには、大きく 2 つの案があります。

  • 案 A　すべて Git に置く：コード、ファイルとして書いたスキーマ、JSON や Markdown のファイルとして書いたコンテンツを、1 つの Git リポジトリに置く。チェンジセットはブランチ、公開はマージに対応する
  • 案 B　ハイブリッド：コードとスキーマは Git に、コンテンツはブランチを持てる版管理付きのストアに置く。チェンジセットは、Git のブランチとコンテンツ側のブランチの組として表す

案 A は、コンテンツの量が限られ、更新の即時性をそれほど求めないサイトに向きます。案 B は、大量のコンテンツを頻繁に更新するサイトに向きますが、2 つのストアをまたいで一括の公開と巻き戻しを実現する仕組みを、自前で作り込む必要があります。

どちらを選んでも、チェンジセット・サイトグラフ・ポリシーという上位の設計は変わりません。SMA ではストレージを SMA コアの下に隠し、エージェントからはどちらの案かが見えないようにします。そうしておけば、小さく案 A で始め、規模が大きくなったら案 B へ移る、という道も残せます。

以下では、設計上の課題が多い案 B を掘り下げます。

案 B のデータモデル

コンテンツストアは、エントリを上書きしません。エントリを編集するたびに、新しいリビジョンを追記します。リビジョンは一度書いたら変更しない不変のデータで、内容・作成者・準拠するスキーマの版・親のリビジョンを持ちます。準拠するスキーマの版を持つので、スキーマが変わったときに、どのエントリに移行が必要かを判定できます。

ブランチは、「どのエントリが、いまどのリビジョンか」の対応表で表します。この対応表をマニフェストと呼ぶことにします。本流も 1 つのマニフェストで、チェンジセットを開くことは、本流のマニフェストを写して自分用のマニフェストを作ることにあたります。写すといっても、変更したエントリの分だけを記録し、残りは元のマニフェストを参照すれば済むので、分岐のコストはほとんどかかりません。

マージはエントリ単位で行います。チェンジセットのマニフェストと本流のマニフェストを、分岐した時点のマニフェスト（共通の祖先）と比べ、片方だけが変えたエントリはそのまま採用し、両方が変えたエントリはフィールド単位で比べます。同じフィールドを両方が変えていれば、構文上の競合です。

これは Git がファイルとディレクトリで行っていることを、エントリとフィールドの単位で行うものです。Git と違うのは、検索や絞り込みのための索引をストアが持てることと、エントリ単位で権限を判定できることです。

一括の公開：リリースの付け替え

案 B の最大の難所は、Git とコンテンツストアという 2 つのストアをまたいで、一括で公開し、一括で巻き戻すことです。2 つのデータベースを同時に更新する分散トランザクションは、作るのも運用するのも困難です。

ここで、両方のストアが「書き換えない版」を持っていることが効いてきます。Git のコミットは不変で、コンテンツのマニフェストも、公開に使う時点で凍結できます。そこで本番のサイトを、リリースという版の組で表します。

  • コードのデプロイ：Git のあるコミットからビルドしたもの
  • スキーマの版：同じコミットに含まれるスキーマ定義
  • コンテンツのマニフェスト：凍結したマニフェスト

本番が見るのは、「本番」という 1 つのポインタが指すリリースだけです。公開とは、新しいリリースを組み立てて検証し、ポインタを付け替えることです。付け替えは 1 か所への書き込みなので、一括で起こります。巻き戻しは、ポインタを前のリリースに戻すだけです。前のリリースが指すコミットもマニフェストも消えていないので、確実に元の姿へ戻れます。

そのためには、フロントエンドが「最新のコンテンツ」ではなく、「リリースが指すマニフェストのコンテンツ」を読む必要があります。静的生成なら、ビルドの時点でマニフェストを固定すれば、ビルドの成果物そのものがリリースになります。リクエストのたびに描画する構成なら、フロントエンドはリリースを指定してコンテンツを問い合わせます。

第6章で見た expand/contract の各段階も、それぞれ 1 つのリリースとして順に付け替えていけば、途中のどの時点でも、本番は整合した版の組を指していることになります。

プレビューと即時反映

プレビューも同じ仕組みで作れます。チェンジセットごとに、ブランチのコードからビルドしたデプロイと、チェンジセットのマニフェストを組にした候補リリースを作り、専用の URL で表示します。コードの変更とコンテンツの変更を合わせた姿を、本番と同じ方法で確認できます。第4章の課題 3 への答えです。

候補リリースは、チェンジセットごとに隔離されたサイトの複製です。Cloudflare OS の Gadget が、隔離されたインスタンスだからこそコードを自由に変えられるのと同じく、候補リリースは本番から切り離されているので、エージェントはその中でコードも構造もコンテンツも自由に変えられます。

コンテンツだけの変更なら、コードのデプロイはそのままに、マニフェストだけを差し替えた新しいリリースを作ります。リクエストのたびに描画する構成なら、ポインタの付け替えだけで即時に反映できます。静的生成の構成でも、変わったエントリに依存するページだけをサイトグラフで特定し、作り直せば済みます。

案 B の難しさ

案 B には、作り込まなければならない部分も多くあります。

  • 古いリビジョンの掃除：どのリリースからも、開いているチェンジセットからも参照されなくなったリビジョンを回収する仕組みが要る。一方で、監査のために残す期間も決める必要がある
  • ブランチ上の検索：本流の索引はストアが持てるが、チェンジセットごとに完全な索引を作るのは重い。本流の索引に、チェンジセットで変えたエントリだけを重ねて検索する、といった工夫が要る
  • 画像などの大きなファイル：リビジョンに直接は入れず、内容のハッシュで参照する。同じファイルは一度だけ保存され、しかも不変なので、マニフェストと同じように版の組に入れられる
  • 人間の同時編集：同じチェンジセットを複数の編集者が同時に編集するなら、エントリ単位でリアルタイムに共同編集する仕組みが別に要る

中間の選択肢：Git 互換のリポジトリを大量に使う

案 A と案 B の間には、もう 1 つの選択肢があります。Git 互換のリポジトリを、1 つではなく大量に使う方法です。

Cloudflare が 2026 年 4 月に発表した Artifacts は、エージェント向けの Git 互換の版管理ストレージで、リポジトリを数千万単位で作れることをうたっています。用途として、コードだけでなく、顧客ごとの設定を巻き戻せる形で持つことも挙げられています（発表時点ではベータ版）。

こうしたストアがあれば、コンテンツをページ・言語・コレクションといった単位で別々のリポジトリに分け、Git のブランチ・差分・マージをそのまま使いながら、巨大な 1 つのリポジトリになるのを避けられます。リリースは複数のリポジトリのコミットの組として表せばよく、上で述べた付け替えの仕組みはそのまま使えます。ただし、検索のための索引は別に作る必要があります。

結びコンテンツ管理から、サイト管理へ

CMS は Content Management System、つまりコンテンツを管理するシステムとして生まれました。ヘッドレス CMS はその「コンテンツ」を純化し、コードから切り離すことで成功しました。

けれど、AI への 1 つの指示がコードも構造もコンテンツも変える時代には、管理すべき単位はコンテンツではなく、サイトそのものです。そして管理の担い手は、人間が操作するシステムから、人間の指示を受けて動くエージェントへと移っていきます。

SMA（Site Management Agent）という名前には、この 2 つの移行を込めました。コード・構造・コンテンツを等しく扱い、複数のエージェントによる変更を受け止め、人間がそのすべてを見渡して承認できる。それが、AI 時代の CMS の理想像だと考えます。
